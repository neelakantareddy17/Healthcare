# Healthcare

Full-stack healthcare and hospital management application with a Node.js/Express/TypeScript backend and a React/Vite frontend. The system supports role-based authentication, doctor discovery, appointment booking, mocked payments, QR check-in, doctor queues, notifications, and admin dashboards.

The backend is the source of truth for authorization and business rules. The frontend uses centralized Axios services and validates persisted sessions through `GET /api/auth/me`.

## Repository layout

```text
Healthcare/
├── backend/       # Express API, Prisma schema, migrations, seed data
├── frontend/      # React/Vite application
├── docs/          # Project documentation
└── screenshots/   # UI reference screenshots
```

The API runs on `http://localhost:5000` by default. The frontend runs on Vite's development port, normally `http://localhost:5173`.

```
│   ├── controllers/           # Thin HTTP layer — request in, response out
│   ├── middlewares/           # auth, role, validate, error handling
│   ├── routes/                # Route definitions only
│   ├── services/               # ALL business logic + Prisma queries
│   ├── validators/            # Zod schemas
│   ├── utils/                 # ApiError, ApiResponse, jwt, hash, qrcode, date
│   ├── socket/                 # Socket.IO server + queue event helpers
│   ├── types/                  # Shared TS types + Express Request augmentation
│   ├── app.ts                  # Express app (middleware + route wiring)

│
├── package.json                # Backend scripts and dependencies
├── tsconfig.json
├── .env.example
└── README.md
```

### Layered architecture rules followed

- **Controllers** — only read `req`, call a service, and send a response via `ApiResponse`. No Prisma calls, no business rules.
- **Services** — all business logic and every Prisma query lives here.
- **Routes** — only wire up `path -> middleware -> controller`. No logic.
- **Validators** — all input validation is done with Zod, applied via the `validate` middleware before the controller runs.

## Frontend

The frontend is a React/Vite application with role-based layouts and routes for patients, doctors, and admins.

```text
frontend/src/
├── components/     # Shared and feature components
├── context/        # Authentication and theme state
├── hooks/          # Reusable React hooks
├── layouts/        # Patient, doctor, admin, and auth layouts
├── pages/          # Role-specific screens
├── routes/         # Private and role route guards
├── services/       # Centralized API calls
└── utils/          # Token, date, and UI helpers
```

Set `VITE_API_URL` when the API is not running at the default address:

```env
VITE_API_URL=http://localhost:5000/api
```

Authentication tokens are stored under `mediq_token` and the cached user under `mediq_user`. On startup, the frontend validates the token with `/auth/me`; it does not trust the cached user by itself.

```bash
cd backend

npm install

# Windows PowerShell
copy .env.example .env

```

Edit `.env` and set your PostgreSQL connection string:

```env

JWT_SECRET=replace_with_a_long_random_string
```

### Database setup (Prisma)

```bash
# Generate the Prisma Client
npm run prisma:generate

# Apply development migrations
npm run prisma:migrate

# (Optional but recommended) seed an Admin + sample Doctor + Department
npm run seed
```

Seeded accounts (from `prisma/seed.ts`):

| Role   | Email                  | Password    |
|--------|-------------------------|-------------|
| Admin  | admin@healthcare.com    | Admin@123   |
| Doctor | doctor@healthcare.com   | Doctor@123  |

> Doctors and Admins **cannot self-register** — only Patients can register via `POST /api/auth/register`. The first Admin must be seeded (as above) or inserted directly into the database; that Admin then creates all further Doctor accounts through the API.

## Authentication

All protected routes expect:

```
Authorization: Bearer <JWT_TOKEN>
```

JWT payload shape:

```json
{ "userId": "uuid", "role": "PATIENT | DOCTOR | ADMIN" }
```

| Rule | Details |
|---|---|
| Patients | Can self-register via `POST /api/auth/register` |
| Doctors  | **Cannot** self-register — created only by an Admin via `POST /api/doctors` |
| Admins   | **Cannot** self-register — seeded once, then manage the system |

### Payments (mocked — no real gateway)
| Method | Endpoint | Auth |
|---|---|---|
| POST | `/payments/:appointmentId/pay` | Patient / Admin |
| GET | `/payments/:id` | Bearer |
| GET | `/payments` | Admin |

**Pay — request**
```json
POST /api/payments/<appointmentId>/pay
{ "method": "UPI" }
```
**Pay — response**
```json
{
  "success": true,
  "message": "Payment successful, appointment confirmed",
  "data": {
    "payment": { "status": "SUCCESS", "amount": "800", "method": "UPI" },
    "qrCode": "data:image/png;base64,....",
    "checkInCode": "b3f1b0e0-...."
  }
}
```
Only a `SUCCESS` payment moves the appointment to `PAID` and returns the backend-generated QR code and check-in code. Queue entry creation occurs when the paid appointment is checked in.

### Queue Management
| Method | Endpoint | Auth | Notes |
|---|---|---|---|
| GET | `/queue/my-queue` | Doctor | Today's queue for the logged-in doctor |
| GET | `/queue/doctor/:doctorId?date=YYYY-MM-DD` | Bearer | Queue for a specific doctor/date |
| POST | `/queue/check-in` | Bearer | Scanning the QR code sends `{ "checkInCode": "..." }`; moves appointment `PAID -> CHECKED_IN` |
| GET | `/queue/:id` | Bearer | |
| PUT | `/queue/:id/status` | Doctor/Admin | body: `{ "status": "IN_PROGRESS" \| "COMPLETED" \| "SKIPPED" \| "WAITING" }` |

**Queue rules enforced in `queue.service.ts` / `payment.service.ts`:**
- Only **paid** appointments receive a token (`createQueueEntryForAppointment` requires `status = PAID`).
- Token numbers **restart every day, per doctor** (computed from `MAX(tokenNumber)` for that doctor+date).
- One **QueueEntry per appointment** (unique constraint) — i.e., one active queue slot per booking.
- QR check-in flips `PAID -> CHECKED_IN` only (`checkInAppointment`).

## Frontend integration status

The frontend currently uses the backend API for:

- Authentication persistence and role routing
- Doctor discovery and doctor details
- Appointment creation, listing, cancellation, and status display
- Mock payment confirmation and backend-generated QR codes
- Patient QR check-in
- Doctor queue reads and queue status updates
- Notifications and individual read actions
- Patient/admin/doctor patient lists
- Admin dashboard totals and revenue

The following areas remain intentionally limited until matching backend contracts are available:

- Medical records and lab results
- Full user management and reporting endpoints
- Doctor schedule and leave screens
- Browser camera QR scanning
- Frontend Socket.IO subscription for live queue updates

The frontend does not duplicate backend authorization or appointment business rules. Client-side route guards are for navigation only; the API remains the security boundary.

## Real-time (Socket.IO)

Connect with a JWT in the handshake:

```js
import { io } from 'socket.io-client';

const socket = io('http://localhost:5000', {
  auth: { token: '<JWT_TOKEN>' },
});

// Doctor dashboards subscribe to a specific doctor's live queue
socket.emit('queue:join', '<doctorId>');

socket.on('queue:update', (queueSnapshot) => {
  console.log('Live queue:', queueSnapshot);
});

socket.on('queue:token-called', ({ tokenNumber }) => {
  console.log('Now serving token:', tokenNumber);
});

// Every authenticated user automatically receives personal notifications
socket.on('notification:new', (notification) => {
  console.log('New notification:', notification);
});
```

Emitted from the backend:
- `queue:update` — whenever a queue entry is created/checked-in/status-changed (`src/socket/queue.socket.ts`)
- `notification:new` — whenever a notification is created for a user (`src/services/notification.service.ts`)

## Error Handling

All errors funnel through a single `errorHandler` middleware (`src/middlewares/error.middleware.ts`) and respond in a consistent shape:

```json
{ "success": false, "message": "Doctor is on leave on the selected date" }
```

Prisma known errors (`P2002` unique constraint, `P2025` not found) are automatically translated to `409`/`404` responses.

## Notes & Assumptions

- Payments are **fully mocked** — `POST /payments/:appointmentId/pay` always succeeds (no external gateway).
- QR check-in uses a UUID `checkInCode` stored on each `Appointment`; `qrcode` renders it as a base64 PNG at payment time.
- The current backend uses Prisma 6 with the schema and migrations under `backend/prisma/`.
- Soft-delete pattern is used for Doctors/Patients (`isActive = false`) to preserve appointment/payment history instead of hard-deleting.
